# 第四部分 · 经典事故反演案例库 (Incident Casebook)

> **真实事故是治理体系唯一的养料。以下 10 则案例全部源自真实生产踩坑，已完全脱敏。**
>
> 每则的结构是固定的：**发生了什么 → 底层不变量 → 编译成的机制**。第三栏若写不出来，说明这次复盘还停在文本层。

---

### 案例 1：精确提交与并发搭车污染（讲“软提醒 vs 硬红线”）
- **事故**：多个 AI 会话并行工作时，某 Agent 在收尾时执行了 `git add -A`，把另一个会话准备中的未完成代码和本地临时文件裹挟推上了远程仓库。
- **错误的沉淀**：在笔记中写“以后 commit 时注意不要多加文件”。（文本软法，必然重犯）。
- **底层不变量**：收尾提交必须显式指定文件清单；`add -A` / `commit -a` 在多会话协作环境下物理不安全。
- **编译成的机制**：L1 宪法硬拦截：收尾 Commit 必须为 `git add <具体文件>` + `git commit -- <paths>`。

---

### 案例 2：可逆第一步与反悔时间窗（讲“不可逆退役二次确认”）
- **事故**：Owner 指令“某频道/服务可以废弃了”，AI 立即执行了彻底删除。10 分钟后 Owner 发现还有依赖要求回滚，但数据已永久丢失。
- **底层不变量**：任何退役或删除操作，第一步必须可逆（改名备份、移入废纸篓、停发）；**不可逆的那一步即使指令是 Owner 本人下达，也必须在现场发起二次显式确认**。
- **编译成的机制**：工具层拦截 `rm` 改走废纸篓；退役资源强制先执行重命名归档，禁止静默物理抹除。

---

### 案例 3：脆弱正则与明文密码泄露（讲“取密只进变量不打印”）
- **事故**：Agent 试图读取含密码的配置文件，使用 `cat file | sed 's/pass/xxx/'` 脱敏输出。由于配置格式微调，脆弱的 sed 正则失效，明文密码打入对话流并永久污染 Session 日志。
- **底层不变量**：从含密文件中读取数据，严禁依赖文本正则过滤后打印；机密一旦进入对话流便无法可靠召回。
- **编译成的机制**：机密只允许通过 1Password CLI 或环境变量在进程间直传；查看配置必须用专用 key 提取工具，禁止 `cat` 整个敏感文件再正则覆盖。

---

### 案例 4：待推提交红与工作树假绿（讲“PUSH_REQUIRES_GREEN_SUITE”）
- **事故**：开发者本地工作区跑单测全绿后 push；但由于本地有个未暂存的辅助文件，远程拉取这批 commit 后编译直接报错（缺少依赖）。
- **底层不变量**：推向主干的凭据必须是“待推提交内容本身”，而不是“本机当前混杂的工作区”。
- **编译成的机制**：Git Pre-push 门禁提取待推 Commit 生成独立镜像执行全量测试，只要有一项红线未过即物理拒推。

---

### 案例 5：否定式断言必须穷举证据（讲“NEGATIVE_CLAIM_NEEDS_HARDER_EVIDENCE”）
- **事故**：Agent 向用户汇报“系统中不存在某个配置/该功能未实现”，用户随后用一条简单查询证明其一直存在，导致决策推导完全偏离。
- **底层不变量**：证明“有”只需要一个命中样本；证明“没有/不存在”必须完成全范围穷举只读取证。
- **编译成的机制**：凡说出“未实现/不存在/无记录”前，必须先执行只读扫描并附带“查验了哪几处”的证据链；证据不足只能降级表述为“在 A/B 处未检索到”。

---

### 案例 6：黑名单必复发（讲“关于如何写规则的元规则”）
- **事故**：某项目同一类错误两度复发。第一次修复时，规则写成了“不要再犯上次那个具体错误”（黑名单）；第二次，同一个底层问题换了个载体出现，黑名单完美漏过。
- **正确的沉淀**：重写规则，断言底层不变量本身，不枚举表象。
- **编译成的机制**：所有门禁按“断言不变量”编写；“沉淀成不变量断言，不是历史坏样本黑名单”升格为元规则。

---

### 案例 7：读侧对称与防规矩烂掉（讲“先查已有资产与 SOP”）
- **事故**：系统已沉淀了某故障的完整解法，但新会话没读旧沉淀，从头开始排查，绕远路还引入了新 Bug。
- **底层不变量**：只写不读 = 沉淀白做。知识库必须有“读侧纪律”：动手排障前先检索资产页与已有 SOP。
- **编译成的机制**：排障入口强制“先查已有 SOP”步骤；定期独立审计沉淀有效性。

---

### 案例 8：总机换壳与死窗精准捕获（讲“进程能力探针 + 失败自动回滚”）
- **事故**：长驻总机在运行两周后转录文件达到几百兆，内存撑满导致进程崩溃，且断线期间遗漏了多条用户消息。
- **底层不变量**：长驻进程必须有物理级生命周期管理；断连恢复后必须给出明确的死窗时间范围。
- **编译成的机制**：50MB 阈值触发原子冷换壳，接管失败自动回滚；看护器每 120 秒巡检并自动重连，主动汇报死窗起止时间。

---

### 案例 9：只走顺路的测试套件（讲“门禁必须证明自己拒绝了什么”）
- **事故**：本仓自己的第一版 `core/`。四个模块各配了单元测试，`Ran 7 tests OK`，两道治理门禁全绿，一路推上主干。事后逐条打失败路径才发现：破坏性拦截钩子在 13 种删除形态里只拦得住 1 种、却误伤 2 种正常命令；任务账本会给一个从未创建过的 task 返回 `closed`，空证据也照关不误；提交树门禁对真实的 Python 依赖 0/2 漏判、对散文里提到的文件名 1/1 误杀；总机换壳模块的 docstring 宣称“接管失败自动回滚”，而换壳、接管、回滚三段代码一行都不存在。
- **为什么全绿**：7 个测试**没有一个打失败路径**。它们断言的是“函数返回了”“退出码是 0”，而这四个模块存在的全部意义是**拒绝**某件事。测试只覆盖被接受的那条路，无论拒绝逻辑是否有效都会通过。
- **错误的沉淀**：在贡献规范里写一句“请为新逻辑补充测试”。（文本软法——上一版的贡献规范里正好有这句，并没有拦住任何东西。）
- **底层不变量**：**一个机制的价值等于它拒绝的集合。只证明它接受什么，等于没有证明。**
- **编译成的机制**：`ops/check_negative_test_coverage.py` 断言 `core/` 每个模块都有对应测试套件、且套件中含真实的否定式断言（`assertRaises` / 非零退出码 / `assertFalse`）；并断言凡是“以拒绝为职责”的模块必须在自己的 docstring 里写明**不覆盖面**。该门禁并入入职门禁与 CI，且它自己也带负向测试（`tests/test_check_negative_test_coverage.py`，用四种不合格套件的样本证明它会拒绝）。
- **附带的一条元教训**：这批代码由一个运行时生成，文档层质量很高、叙事完全站得住，**代码层与它自己的文档宣称脱节**。所以这条门禁断言的不是“某个运行时不可信”，而是“任何执行者交上来的机制，都必须自带拒绝证明”——这正是 `docs/03` 多模型解耦的要求：**换个模型不该换一套防线**。

---

### 案例 10：会挂起的门禁（讲“fail-closed 不等于 block-forever”）
- **事故**：就在编写案例 9 那道门禁的同一个 session 里。新版拦截钩子支持从 stdin 读取 hook payload，用的是 `payload="$(cat)"`。当调用方没给 argv、而 stdin 是一个**始终不关闭**的管道时，`cat` 永久阻塞——组合门禁跑到第 29 个用例就停在那里不动了，没有任何报错。
- **为什么危险**：从外面看，一个挂住的钩子和一个卡住的任务**完全无法区分**。它既不放行也不拒绝，把调用它的 agent 一起锁死；而"钩子超时"通常没有告警，于是它是一次**静默的全线停摆**。
- **底层不变量**：**fail-closed 的语义是"拒绝"，不是"永不返回"。** 任何位于工具边界上的同步钩子，其所有输入路径都必须有界；无界等待不是保守，是另一种失败模式。
- **第二个不变量（同一次修复中暴露）**：按行读取时，**最后一行若没有换行符会被静默丢弃**（`read` 在 EOF 返回非零，但已经赋过值）。单行 JSON payload 因此被当成"空 payload"——而空 payload 走的是**放行**分支。一个读取 bug 把 fail-closed 悄悄翻转成了 fail-open。
- **编译成的机制**：stdin 读取改为有界（`read -t`，超时可配），并用 `|| [[ -n "$_line" ]]` 收尾行；新增回归测试 `test_does_not_block_on_a_stdin_that_never_closes`——打开管道、什么都不写、断言进程在超时内自行退出。同时所有 argv 模式的测试调用改为 `stdin=DEVNULL`，因为 argv 模式本就不该碰 stdin。
- **它是怎么被抓到的**：不是靠代码审阅，是靠**把门禁真的跑起来**。案例 9 那道新门禁把测试套件并进了入职门禁，于是这个挂起当场发生在作者面前。这正是复利飞轮的样子——新装的机制在同一个 session 里抓到了下一个 bug。

---

## 关于转述这些机制的一条纪律

上面每一则的“编译成的机制”都对应 `core/` 或 `ops/` 里的一个真实脚本，而**每个脚本都在自己的 docstring 里写明了不覆盖面**。转述、引用或移植这些门禁时，**必须把不覆盖面一并带走**。

原因是不对称的：一道被误以为覆盖更广的门禁，比没有门禁更危险——没有门禁时人还会自己小心，误以为有门禁时不会。例如 `check_commit_standalone.py` 只能看见**字面量**引用，运行时拼接出来的路径它完全看不到；它通过只说明“没有悬空的字面量引用”，不说明“这棵树是自洽的”。这句话必须跟着门禁走。
