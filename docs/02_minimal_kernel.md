# 第二部分 · 最小内核与新手起步 (The Minimal Kernel)

> **“不要给 Agent 更多的劝告，给它一道不可逾越的物理门禁。”**

---

## 1. 四条基本法（Core Fundamental Laws）

这四条基本法是任何多 Agent 协作系统不可违背的底层公理：

1. **判断归模型，确定性归脚本（Model Judgment vs Deterministic Boundary）**：
   - 模型只负责语义理解、模糊分类、起草与总结；
   - 路由、重试、状态裁决、格式校验必须下沉到脚本与门禁，不靠 Agent 临场口头承诺。
2. **冲突必须摆上台面（Conflicts Surface Authority）**：
   - 遇到两套冲突的规则、数据源或代码模式时，Agent 必须显式指出冲突，选择权威源并标记被排除项；禁止混合折中后假装一致。
3. **验证的是意图，不是“命令跑过”（Intent Validation）**：
   - 测试通过或命令退出码为 0，不等于达成了业务意图；
   - 每次验证必须说明验证了什么用户意图、哪些失败边界未覆盖。
4. **一切降级必须大声说（Fail Loud）**：
   - 任何跳过、未验证、部分完成、工具降级、权限阻断都必须显性汇报；“默认成功”是治理体系中最昂贵的谎言。

---

## 2. 事故复利飞轮（The Compounding Loop）

系统通过以下五步闭环实现自我免疫：

```
生产事故/异常 → 反演底层不变量 → 当天编译为硬门禁 → 自动化测试验证存活 → 周期性独立审计
     ↑                                                                    |
     └──────────────── 审计发现门禁失效 = 新事故，重新入环 ←────────────────┘
```

### 两条元规则（Meta-Rules）：
- **元规则一：沉淀底层不变量，不是历史坏样本黑名单**：
  落门禁时必须断言底层不变量本身，严禁仅枚举出过事的具体表象。黑名单式门禁换个载体必然被击穿。
- **元规则二：写进日志 ≠ 已沉淀**：
  “我记住了/已记录文档”不代表沉淀完成；只有当规则进入门禁脚本或测试套件并当场跑绿，才算闭环。

---

## 3. 新手第零天：三个文件起步（Three Files to Start）

在刚开始使用本体系时，不需要立刻部署复杂的全家桶，只需要在项目根目录创建 3 个文件：

```
my-project/
├── RULES.md         # 1. 宪法 (人机顶层不变量与不可逾越红线)
├── INCIDENTS.md     # 2. 事故簿 (事故复盘四要素)
└── CLOSEOUT.md      # 3. 收尾清单 (会话结束前的核验单)
```

### 3.1 宪法（`RULES.md`）
定义不可突破的红线（建议 ≤ 10 条，一页以内），如：
- 禁止 `rm` 操作，删除必须走废纸篓；
- 提交前测试必须全量通过；
- 机密禁止明文进入对话流。

### 3.2 事故簿（`INCIDENTS.md`）
记录四要素结构化复盘：
1. **发生了什么**（现象）；
2. **底层不变量是什么**（为什么出事）；
3. **编译成了什么机制**（落到了哪个门禁/脚本）；
4. **怎么验证它活着**（自动化测试命令）。

### 3.3 收尾清单（`CLOSEOUT.md`）
会话结束前 Agent 必须逐项核对并汇报：
- 改动了哪些路径；
- 跑了哪些意图验证；
- 留存了哪些未决事项需要人类拍板。
